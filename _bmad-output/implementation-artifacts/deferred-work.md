## Plattform-Item 2026-04-24: Idempotency-Keys für Mutationen (aus Story-3.2 Review)

Bei Mid-Bulk-Network-Loss erzeugt der client-seitige Retry (`queries.ts` `useChangePsaProfil`) eine zweite `propagationGroupId` und einen doppelten Audit-Trail-Eintrag — gleiche Logik betrifft alle anderen Eigenschutz-/Sicherheits-Mutationen (Sicherheitsregeln, Gefährdungsbeurteilung, ETB) und gehört architektonisch in eine eigene Plattform-Story.

**Optionen für Folge-Story:**

- **(a) Idempotency-Key-Header:** Frontend generiert pro Submit eine UUID (`Idempotency-Key`-Header), Backend dedupliziert via Outbox/Cache mit z. B. 60s-TTL. Standard-REST-Pattern, gut testbar.
- **(b) Frontend-Mutation-ID + Server-Side-Dedup-Cache:** Client generiert UUID im Mutation-Body, Server-Side hält 60s-Cache mit (userId, mutationId, hash) → bei Duplicate-Request liefert er den gecachten Response. Erfordert Cache-Layer im Backend.
- **(c) Bewusst ignorieren:** Audit-Trail-Doppel ist akzeptabel, Sicherheitsbeauftragter erkennt's im Verlauf. Niedrigster Aufwand, höchstes Risiko.

**Empfehlung Plattform-Pattern:** (a) Idempotency-Key-Header — Standard, testbar, erweiterbar. Sollte vor Live-Deployment der Eigenschutz-Module entschieden werden.
