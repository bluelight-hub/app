## 3. Herausforderungen (Challenges)

### Challenge #1: `import type` bricht NestJS DI - 7x gefixt
**Story 1.1, 1.3, 1.4 (und weitere)**

**Problem:**
TypeScript `import type` entfernt Runtime-Symbole → NestJS kann nicht injecten.

**Konkret:**
```typescript
// ❌ FALSCH - Story 1.1 Initial
import type { TokenHash } from '@/domain/value-objects/token-hash';

// ✅ RICHTIG - Story 1.1 Fix
import { TokenHash } from '@/domain/value-objects/token-hash';
```

**Impact:**
- 7x über verschiedene Stories gefixt
- Code Review fand es in Story 1.1 (C1), 1.3 (HIGH #6.2)
- Pattern wurde in `.cursorrules` nicht dokumentiert

**Action Item:** Lint-Rule erstellen + dokumentieren.

---

### Challenge #2: Repository-Abstraction vs. direkter Prisma-Zugriff
**Story 1.3**

**Problem:**
Handler in Story 1.3 griff direkt auf `prisma.user` zu statt via `IUserRepository`:

```typescript
// ❌ FALSCH - Story 1.3 Initial
const adminCount = await tx.user.count({ where: { role: { in: ['ADMIN', 'SUPER_ADMIN'] } } });

// ✅ RICHTIG - Story 1.3 Fix
const adminCount = await this.userRepo.countByRoles(['ADMIN', 'SUPER_ADMIN'], tx);
```

**Impact:**
- HIGH Issue #6.1 in Code Review
- Repository musste um `countByRoles()` und `setPasswordHash()` erweitert werden
- Architectural Pattern jetzt klar: **IMMER über Repository, nie direkter DB-Zugriff**

**Lesson:** Hexagonal Architecture erfordert konsequente Abstraction-Layers.

---

### Challenge #3: bcrypt Cost Factor nicht compile-time validated
**Story 1.1, 1.6**

**Problem:**
NFR-S1 verlangt `bcrypt cost factor >= 10`, aber Code nutzt Magic Number:

```typescript
// ❌ Schwach - keine Type-Safety
const hash = await bcrypt.hash(rawToken, 10);
```

**Impact:**
- Developer könnte versehentlich `5` nutzen → Security-Violation
- Keine Compile-Time-Garantie

**Vorgeschlagene Lösung:**
```typescript
// ✅ Type-Safe
const BCRYPT_COST_FACTOR = 10 as const;
type ValidCostFactor = typeof BCRYPT_COST_FACTOR extends infer T extends number ? (T extends 10 | 11 | 12 ? T : never) : never;
```

**Action Item:** Type-Level-Constant mit Validation.

---

### Challenge #4: Concurrent-Tests sind flaky mit Mocks
**Story 1.1a, 1.2**

**Problem:**
Guards mit `setImmediate()` für async Updates → Test-Timing-Issues:
- `lastUsedAt` Update passiert asynchron
- Tests müssen `await new Promise(resolve => setImmediate(resolve))` nutzen
- Flakiness bei parallelen Test-Runs

**Impact:**
- Test-Suite Runtime +20% wegen Wait-Logik
- Developer Experience: Tests intermittent failing

**Lesson:** Async Guards brauchen Test-Utilities mit expliziten Flush-Mechanismen.

---

### Challenge #5: Domain vs. Integration Events - Boundary unklar
**Story 1.6, 1.7**

**Problem:**
Wann emittiert man `DomainEvent` vs. `IntegrationEvent`?
- Story 1.6: `InviteCodeCreatedEvent` → Integration Event für Email-Service
- Story 1.7: `InviteCodeRevokedEvent` → Sollte das Email-Service benachrichtigen?

**Diskussion:**
- Domain Event: Interne Business-Logic
- Integration Event: Cross-Bounded-Context

**Resolution:**
Event-Adapter Pattern in `infrastructure/events/adapters/` transformiert Domain → Integration Events.

**Action Item:** Pattern dokumentieren.

---

### Challenge #6: Form-Validation dupliziert (Frontend + Backend)
**Story 1.3, 1.3a**

**Problem:**
Validation-Logic in Zod-Schema (Backend DTO) UND @tanstack/react-form (Frontend):
- `username` min/max length
- `password` complexity rules
- Error Messages unterschiedlich

**Impact:**
- 2x Maintenance-Aufwand
- Risk of Drift

**Vorgeschlagene Lösung:**
Shared Zod-Schemas in `@bluelight-hub/shared`:
```typescript
// packages/shared/schemas/auth.ts
export const usernameSchema = z.string().min(3).max(20);
```

**Action Item:** Shared Schema Package erstellen.

---

### Challenge #7: OpenAPI Schema braucht Custom-Decorator
**Story 1.3, 1.6, 1.7 - AC7 Compliance**

**Problem:**
Standard `@ApiOkResponse` generiert Schema ohne `WrappedResponse<T>` Wrapper:

```typescript
// ❌ Generiert: { data: SetupResponseDto } - FALSCH
@ApiOkResponse({ type: SetupResponseDto })

// ✅ Generiert: { data: SetupResponseDto, meta: {...} } - RICHTIG
@ApiWrappedResponse(SetupResponseDto)
```

**Impact:**
- 4x in Code Reviews gefangen (Story 1.3, 1.6, 1.7)
- Frontend-API-Client generiert falsche Types

**Action Item:** Refactor zu Generic `@ApiWrappedResponse` Decorator.

## 4. Key Insights & Learnings

### Insight #1: Guard-Order ist KRITISCH
**Story 1.1a, 1.2**

**Erkenntnis:**
`SetupPendingGuard` MUSS vor `ServerAccessGuard` kommen:
- Im Setup-Mode existieren keine Tokens
- `ServerAccessGuard` würde `401 Unauthorized` werfen
- `SetupPendingGuard` wirft `503 Service Unavailable`

**Guard-Order:**
`ThrottlerGuard → SetupPendingGuard → ServerAccessGuard → JwtAuthGuard`

**Lesson:** Guard-Fehler-Codes sind Teil der API-Contract - Order matters!

---

### Insight #2: Computed Fields vs. DB-Persistierung
**Story 1.7**

**Erkenntnis:**
`InviteCodeStatus` kann zur Laufzeit berechnet werden (Priorität: `REVOKED > EXPIRED > USED > ACTIVE`).

**Entscheidung:**
- ✅ Computed Field für MVP (<1000 Einträge)
- ⚠️ DB-View oder Indexed Computed Column für Scale (>1000 Einträge)

**Tradeoff:**
Memory-Filter einfacher zu maintainen, aber skaliert nicht. Dokumentiert als Technical Debt.

---

### Insight #3: Idempotente Delete-Operationen
**Story 1.7**

**Erkenntnis:**
HTTP DELETE sollte idempotent sein → mehrmaliger Aufruf = gleicher State.

**Implementierung:**
```typescript
// revoke() gibt Result.ok() wenn bereits revoked ODER used
// Status wechselt NICHT zu "revoked" wenn useCount >= maxUses
```

**Lesson:** Idempotenz ≠ Zustandsverwandlung - Status-Priorität beachten!

---

### Insight #4: Adversarial Reviews finden 2-3x mehr Issues
**Story 1.1 vs. 1.3**

**Daten:**
- Story 1.1 (Self-Review): 4 CRITICAL
- Story 1.3 (Adversarial Review mit Opus 4.5): 19 Issues (7 HIGH)

**Lesson:**
Quality Gates mit externem Review (anderes LLM, andere Perspektive) sind kritisch für komplexe Stories.

**Action Item:** Adversarial Review für alle Stories >5 SP standardisieren.

---

### Insight #5: Async Guards brauchen Test-Utilities
**Story 1.1a, 1.2**

**Problem:**
Guards mit `setImmediate()` → Test-Timing-Issues.

**Lösung:**
Test-Utilities mit expliziten Flush-Mechanismen:
```typescript
// Test Helper
export const flushAsyncUpdates = () => new Promise(resolve => setImmediate(resolve));
```

**Lesson:** Async-Patterns brauchen dedizierte Test-Infra.

## 9. Significant Discovery Alert

### 🚨 Discovery #1: Platform Storage komplexer als geplant

**Entdeckung (Story 1.3a, 1.7a):**
localStorage ist nicht ausreichend für Browser-Variante:
- localStorage = unencrypted (NFR-S4 verletzt)
- IndexedDB = komplexer, aber verschlüsselbar via Web Crypto API

**Impact auf Epic 2:**
Story 2.1 (Platform Storage Adapter) ist underestimated:
- **Ursprünglich:** 3 SP (nur Tauri vs. localStorage Switch)
- **Neu:** 5 SP (Tauri Store + IndexedDB mit Encryption)

**Empfohlene Änderung:**
Story 2.1 neu-estimaten auf **5 SP** + zusätzliche Research-Task.

---

### 🚨 Discovery #2: Deep-Link-Handling ist OS-spezifisch

**Entdeckung (während Epic 1 Research):**
Deep Links müssen pro OS registriert werden:
- macOS: `Info.plist` + URL Scheme
- Windows: Registry Entry
- Linux: `.desktop` File

**Impact auf Epic 2:**
Story 2.4 (Deep Link Integration) sollte gesplittet werden:
- **Story 2.4a (3 SP):** Deep Link Schema Definition + macOS
- **Story 2.4b (3 SP):** Windows + Linux Support

**Empfohlene Änderung:**
Story 2.4 splitten in 2.4a + 2.4b.

---

### 🚨 Discovery #3: Invite-Code-Exchange braucht Rate-Limiting

**Entdeckung (Story 1.6, 1.7 Code Review):**
Invite-Codes können brute-forced werden ohne Rate-Limiting.

**Impact auf Epic 2:**
Story 2.3 (Invite-Code Exchange Endpoint) braucht:
- `@nestjs/throttler` Guard
- Rate-Limit: Max 5 Einlösungen/Minute/IP (NFR-S3)

**Empfohlene Änderung:**
Story 2.3 von **5 SP → 6 SP** (inkl. Rate-Limiting Implementation + Tests).
