## Story

**As a** System,
**I want** Points of Interest (POIs) für Lagekarten verwalten,
**so that** ich Einsatzorte, Fahrzeuge, Gefahrenquellen und Versorgungspunkte strukturiert speichern kann.

---

## Prerequisites

Diese Story setzt folgende Voraussetzungen voraus:

- ✅ **Bestehende Einsatz-API:** `EinsatzService.findById(einsatzId)` liefert `einsatz.einsatzort` (Adresse)
- ✅ **Prisma ist konfiguriert:** PostgreSQL 17 Database läuft, Prisma-Client generiert
- ✅ **JWT-Authentication:** `JwtAuthGuard` existiert für Route-Protection
- ⚠️ **Story 48.1 (Frontend) optional:** Kann parallel entwickelt werden, da Backend-only Story

**Hinweis:** Diese Story ist backend-fokussiert und kann unabhängig von Story 48.1 (Frontend) implementiert werden.

---

## Acceptance Criteria

1. Prisma-Schema erweitert: `Lagekarte`, `LagekartePoi`, `PoiType` (Enum)
2. Migration: Lagekarte wird beim ersten Load automatisch erstellt
3. Initialer POI (Typ: EINSATZORT) wird aus `einsatz.einsatzort` geocoded
4. Geocoding-Service: Nominatim-API konvertiert Adressen → Koordinaten
5. POI-CRUD-API (8 Endpoints, siehe oben)
6. Geocoding-Ergebnis wird in `LagekartePoi` gespeichert
7. Rate-Limiting: Max. 1 Geocoding-Request/Sekunde

**Integration Verification:**

- IV1: Bestehende Einsatz-Erstellung funktioniert (Lagekarte lazy erstellt)
- IV2: POI-API liefert typisierte POIs (Type-Safety)
- IV3: Migration-Rollback getestet

### Backend Module Architecture

[Source: docs/development/coding-standards.md#Backend (NestJS + TypeScript)]

**Module Pattern (Controller → Service → Repository):**
```typescript
// Lagekarte-Module Structure:
// 1. Controller: HTTP endpoints (REST API)
// 2. Service: Business logic (orchestration)
// 3. Repository: Data access (Prisma queries)
// 4. DTO: Data transfer objects (validation)
// 5. Entities: Domain models (TypeScript interfaces)

// Example Service Pattern:
@Injectable()
export class LagekarteService {
  constructor(
    private readonly repository: LagekarteRepository,
    private readonly poiService: PoiService,
    private readonly geocodingService: GeocodingService,
  ) {}

  async getOrCreateLagekarte(einsatzId: string): Promise<Lagekarte> {
    // Check if exists
    let lagekarte = await this.repository.findByEinsatzId(einsatzId);
    if (!lagekarte) {
      // Lazy creation
      lagekarte = await this.repository.create(einsatzId);
      await this.createInitialPoi(einsatzId);
    }
    return lagekarte;
  }
}
```

### Geocoding Strategy

[Source: docs/bmad/prd/lagekarte-prd.md#2.1 Functional Requirements]

**Geocoding Flow:**
1. User provides `adresse` (string) OR manual `latitude`/`longitude` (numbers)
2. If `adresse` provided:
   - Call Nominatim API (rate-limited to 1 req/s)
   - Parse response: `[{ lat: "51.1234", lon: "10.5678" }]`
   - Store `latitude` and `longitude` in `LagekartePoi`
3. If geocoding fails OR no address:
   - Fallback: Use manual coordinates from frontend
   - Frontend will show error toast: "Geocoding failed, please place POI manually"

**Rate-Limiting Implementation:**
```typescript
// Use @nestjs/throttler
@Injectable()
export class GeocodingService {
  @Throttle({ default: { limit: 1, ttl: 1000 } }) // 1 req per 1000ms
  async geocodeAddress(address: string): Promise<{ lat: number, lon: number } | null> {
    // Nominatim API call
  }
}
```

### POI-Type Enum Details

[Source: docs/bmad/features/lagekarte/epic-48-lagekarte.md#Dependencies & External Libraries]

**12 POI-Types for Katastrophenschutz:**
1. **EINSATZORT:** Haupt-Alarmierungsadresse (primary incident location)
2. **EINSATZABSCHNITT:** Abschnitt A, B, C (incident sectors)
3. **EINSATZLEITUNG:** Einsatzleitstelle, Führungsstelle (command post)
4. **FAHRZEUG:** Statisch platzierte Fahrzeuge (parked vehicles)
5. **EINHEIT:** Statisch platzierte Einheiten (deployed units)
6. **GEFAHRENQUELLE:** Punktuelle Gefahr (hazard source, e.g., gas leak)
7. **SPERRBEREICH:** Absperrpunkt (entry to restricted zone)
8. **VERSORGUNGSPUNKT:** Wasser, Strom, Verpflegung (supply point)
9. **BEREITSTELLUNGSRAUM:** Bereitstellung von Einheiten/Material (staging area)
10. **BEHANDLUNGSPLATZ:** Verletzten-Versorgung (casualty treatment point)
11. **SAMMELSTELLE:** Betroffenen-/Helfer-Sammelpunkt (assembly point)
12. **UNTERKUNFT:** Notunterkunft (emergency shelter)
13. **SONSTIGES:** Custom POI (fallback for undefined types)

## Security Considerations

[Source: docs/development/coding-standards.md#Security Standards]

**Authentication & Authorization:**
- ✅ **All routes protected:** `@UseGuards(JwtAuthGuard)` auf Controller-Ebene
- ✅ **einsatzId Validation:** Route-Parameter werden von NestJS validiert
- ✅ **No public endpoints:** POI-API ist nur für authentifizierte User

**External API Security:**
- ✅ **Nominatim Rate-Limiting:** `@Throttle` decorator (1 req/s) verhindert API-Missbrauch
- ✅ **User-Agent Header:** `User-Agent: BluelightHub/1.0` erforderlich laut Nominatim Policy
- ✅ **Fallback bei Failure:** Geocoding-Fehler führen zu `null`, nicht zu Systemausfall

**Data Validation:**
- ✅ **DTO Validation:** `class-validator` prüft alle Inputs (Enum, String-Length, Number-Range)
- ✅ **SQL Injection Prevention:** Prisma nutzt Prepared Statements (automatisch)
- ✅ **JSONB Validation:** `state` und `metadata` Felder sind typisiert (GeoJSON-Schema)

**Data Protection:**
- ⚠️ **POI-Daten sensibel:** POIs können Gefahrenquellen, Standorte enthalten
  - **Mitigation:** Nur authentifizierte User mit Zugriff auf Einsatz dürfen POIs sehen
- ✅ **Cascade Delete:** Einsatz gelöscht → Lagekarte + POIs automatisch gelöscht (DSGVO-konform)

**Security Testing:**
- [ ] Test: Unauthenticated request → 401 Unauthorized
- [ ] Test: Invalid einsatzId → 404 Not Found
- [ ] Test: Rate-Limiting → 429 Too Many Requests (2nd request within 1s)
- [ ] Test: SQL Injection attempt in `name` field → Rejected by Prisma
