== Status

Accepted

== Kontext

Das Bluelight-Hub-System verwaltet kritische Einsatzdaten für Rettungsorganisationen. Diese Daten unterliegen strengen rechtlichen und regulatorischen Anforderungen bezüglich ihrer Aufbewahrung und Nachvollziehbarkeit. Es besteht die Notwendigkeit, eine klare Policy für den Umgang mit der "Löschung" von Einsatzdaten zu definieren.

=== Problemstellung

* Einsatzdaten können als Beweismittel in rechtlichen Verfahren dienen
* Gesetzliche Aufbewahrungsfristen müssen eingehalten werden
* Vollständige Audit-Trails sind für Compliance-Prüfungen erforderlich
* Versehentliche Löschungen könnten zu rechtlichen Konsequenzen führen
* Historische Daten sind für Analysen und Verbesserungen wichtig

== Entscheidung

Wir implementieren eine strikte **No-Delete Policy** für Einsätze:

1. **Keine physische Löschung**: Einsatzdatensätze werden niemals aus der Datenbank entfernt
2. **Soft-Delete Pattern**: Stattdessen wird ein Status `ARCHIVIERT` verwendet
3. **Kein DELETE-Endpoint**: Die API bietet keinen DELETE-Endpoint für Einsätze
4. **Archive-Funktion**: Ein spezieller Archive-Endpoint markiert Einsätze als archiviert

=== Technische Umsetzung

[source,typescript]
----
// ❌ VERBOTEN: Physische Löschung
@Delete(':id')
async delete(@Param('id') id: string) {
  // NIEMALS IMPLEMENTIEREN!
}

// ✅ ERLAUBT: Archivierung
@Patch(':id/archive')
async archive(@Param('id') id: string) {
  return this.einsatzService.archive(id); // Setzt Status auf ARCHIVIERT
}
----

== Konsequenzen

=== Positive Konsequenzen

* **Rechtliche Sicherheit**: Erfüllung aller gesetzlichen Aufbewahrungspflichten
* **Vollständiger Audit-Trail**: Lückenlose Nachvollziehbarkeit aller Aktivitäten
* **Datensicherheit**: Schutz vor versehentlichem Datenverlust
* **Wiederherstellbarkeit**: Archivierte Einsätze können reaktiviert werden
* **Historische Analysen**: Vollständige Datenhistorie für Auswertungen verfügbar

=== Negative Konsequenzen

* **Speicherplatzbedarf**: Kontinuierliches Wachstum der Datenbank
* **Performance**: Potenzielle Verlangsamung bei sehr großen Datenmengen
* **Datenschutz**: Spezielle Prozesse für DSGVO-konforme Löschung personenbezogener Daten erforderlich
* **Komplexität**: Filterlogik für archivierte Daten in allen Abfragen notwendig

== Alternativen

=== Alternative 1: Physische Löschung nach Aufbewahrungsfrist
* **Verworfen**: Zu hohes rechtliches Risiko, komplexe Fristenverwaltung

=== Alternative 2: Separate Archiv-Datenbank
* **Verworfen**: Erhöhte Komplexität, erschwerte Wiederherstellung

=== Alternative 3: Event Sourcing
* **Verworfen**: Zu komplex für aktuelle Anforderungen, kann später ergänzt werden

== Implementierungsdetails

=== Datenbank-Schema

[source,sql]
----
CREATE TYPE einsatz_status AS ENUM (
  'ANGELEGT',
  'IN_BEARBEITUNG',
  'ABGESCHLOSSEN',
  'ARCHIVIERT'  -- Soft-Delete Status
);

-- Kein CASCADE DELETE auf Foreign Keys
ALTER TABLE related_table
  ADD CONSTRAINT fk_einsatz
  FOREIGN KEY (einsatz_id)
  REFERENCES einsatz(id)
  ON DELETE RESTRICT;  -- Verhindert Löschung
----

=== API-Design

* `GET /einsatz` - Listet standardmäßig nur nicht-archivierte Einsätze
* `GET /einsatz?includeArchived=true` - Optionale Inklusion archivierter Einsätze
* `PATCH /einsatz/:id` - Update erlaubt
* `PATCH /einsatz/:id/archive` - Archivierung
* `DELETE /einsatz/:id` - **NICHT VORHANDEN**

=== Filterung in Queries

[source,typescript]
----
// Standard-Query filtert archivierte Einsätze
const activeEinsaetze = await prisma.einsatz.findMany({
  where: {
    status: { not: 'ARCHIVIERT' }
  }
});
----

== Monitoring und Wartung

* **Regelmäßige Audits**: Vierteljährliche Überprüfung der Archivierungspraxis
* **Performance-Monitoring**: Überwachung der Query-Performance bei wachsender Datenmenge
* **Speicher-Management**: Jährliche Evaluierung der Speichernutzung
* **Compliance-Reviews**: Halbjährliche Überprüfung der rechtlichen Anforderungen

== Ausnahmen

1. **DSGVO-Anfragen**: Personenbezogene Daten müssen auf Anfrage anonymisiert werden
2. **Testumgebungen**: In Dev/Test können Daten gelöscht werden
3. **Datenbank-Migration**: Mit expliziter Genehmigung und vollständigem Backup
