## Was nicht gut gelaufen ist

### Bug-Pattern-Analyse (Top 3 wiederkehrende Probleme)

#### 1. Event-Serialisierung/Registrierung (4 Bugs)

**Problem:** Jedes neue Domain Event muss an **4 separaten Stellen** registriert werden:
1. `event-serializer.ts` (1008 Zeilen, 50+ cases)
2. `event-deserializer.ts` (1694 Zeilen)
3. `event-adapters.module.ts`
4. `adapters/index.ts`

**Root Cause:** Klassisches "Shotgun Surgery" Anti-Pattern. Vergessene Registrierungen bei 4 von 16 Bug-Fixes.

#### 2. DI-Import Bugs (3 Bugs)

**Problem:** TypeScript's `import type` optimiert Imports weg, was NestJS DI zur Laufzeit bricht.

**Root Cause:** Biome's `useImportType` Regel kollidiert mit NestJS DI-Anforderung. Manuelle `biome-ignore` Kommentare sind fehleranfällig. Pre-Commit Hook fängt nicht alle Fälle ab.

#### 3. Frontend-Backend-Schnittstellen-Drift (3 Bugs)

**Problem:** Event-Type-Keys und Response-Wrapping stimmten nicht zwischen Frontend und Backend überein.

**Root Cause:** Fehlende Contract-Tests. 11+ `as unknown as` Type-Casts im Frontend zeigen DTO-Generierungs-Diskrepanzen.

### Architektonische Probleme

#### KRITISCH: Erinnerung Entity ist ein God Object

- **1507 Zeilen**, 30+ private Fields, **37+ Constructor-Parameter**
- Vereint: Lifecycle, Soft-Delete, Snoozing, Zuweisung, Eskalation, Intensivierung, Recurring, ETB-Referenz, Notiz-Referenz, Kategorie
- Verletzt Single Responsibility Principle
- Schwer wartbar, testbar und erweiterbar

#### HOCH: Direkte Prisma-Zugriffe in Application Handlers

- `create-erinnerung.handler.ts` castet `tx as Prisma.TransactionClient`
- Greift direkt auf `prismaTx.etbEintrag.findUnique()`, `prismaTx.kategorie.findUnique()` zu
- **Layer-Verletzung:** Application-Schicht greift auf Infrastructure-Details zu

#### MITTEL: Fehlende Erinnerungsvorlage Domain Entity

- Existiert nur als Prisma-Model ohne Domain Entity
- Keine Domain-Logik, keine Invarianten-Prüfung, keine Events

#### MITTEL: Inkonsistente Event-Namenskonventionen

- Parallel: Dot-Notation (`erinnerung.erstellt`) und PascalCase (`ErinnerungErstellt`)
- Kompatibilitäts-Aliases im Deserializer als Workaround

### Code-Qualität Probleme

- **ErinnerungCard: 789 Zeilen** - deutlich zu große Komponente
- **console.log Debug-Statements** im Produktionscode (QuickCreateErinnerungDialog)
- **Dead Code:** `_assignedToName` wird nie verwendet
- **WebSocket Authorization TODO** offen (Sicherheitsrisiko)

## Key Takeaways

1. **Organisches Wachstum braucht Refactoring-Pausen:** 57 Commits haben das Erinnerung-Entity zum God Object gemacht. Vor neuen Features muss aufgeräumt werden.

2. **"Shotgun Surgery" ist der Top-Bug-Verursacher:** Die 4-Stellen-Event-Registrierung hat allein 4 der 15 Bug-Fixes verursacht. Automatisierung ist Pflicht.

3. **Architektur-Tests sind Gold wert:** Die automatisierten Layer-Guards haben weitere Verletzungen verhindert. Dieses Pattern auf Event-Registrierung erweitern.

4. **Business Value ist herausragend:** Eskalationsketten und Führungsrhythmus-Templates sind echte Alleinstellungsmerkmale für Blaulicht-Organisationen.

5. **Bug-to-Feature Ratio von 1:3 ist akzeptabel** für diese Komplexität, aber die meisten Bugs waren keine Logik-Fehler sondern vergessene Registrierungen und Import-Probleme - also vermeidbar.
