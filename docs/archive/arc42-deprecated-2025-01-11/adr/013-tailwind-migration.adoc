= ADR-013: Migration von Chakra UI zu Tailwind CSS + Headless UI
:author: Bluelight-Hub Team
:revnumber: 1.0.0
:revdate: 2025-08-17
:status: Akzeptiert

== Status

Akzeptiert

== Kontext

Das Frontend des Bluelight-Hub-Systems wurde initial mit Chakra UI als UI-Framework entwickelt.
Nach mehreren Monaten der Entwicklung haben sich verschiedene Herausforderungen ergeben:

* **Bundle-Size**: Chakra UI mit Emotion Runtime führte zu einer erheblichen Bundle-Größe
* **Performance**: CSS-in-JS Runtime-Overhead beeinträchtigte die Performance, besonders auf mobilen Geräten
* **Komplexität**: Die Abstraktion von Chakra UI erschwerte teilweise die Anpassung an spezifische Design-Anforderungen
* **Dependency Management**: Viele transitive Abhängigkeiten erhöhten die Wartungskomplexität
* **Tauri-Kompatibilität**: Optimierungen für die Desktop-App waren mit CSS-in-JS schwieriger umzusetzen

== Entscheidung

Wir migrieren das gesamte Frontend-UI-System von Chakra UI zu:

* **Tailwind CSS**: Utility-First CSS Framework für Styling
* **Headless UI**: Unstyled, accessible Komponenten für komplexe UI-Patterns
* **Atomic Design Pattern**: Strukturierte Component-Hierarchie (atoms, molecules, organisms, templates, pages)

=== Technologie-Stack

[cols="1,2,3",options="header"]
|===
|Komponente |Technologie |Zweck
|Styling |Tailwind CSS 3.x |Utility-First CSS, Zero-Runtime, optimierte Build-Size
|UI Components |Headless UI |Accessible, unstyled Komponenten (Dialogs, Dropdowns, etc.)
|Icons |Heroicons |Tailwind-kompatible Icon-Library
|Build |@tailwindcss/vite |Optimierte Integration mit Vite
|Utils |clsx + tailwind-merge |Conditional Classes und Konflikt-Resolution
|===

== Alternativen

=== Alternative 1: Bei Chakra UI bleiben

* **Pro**: Keine Migration nötig, bestehendes Know-how
* **Contra**: Performance-Probleme bleiben, Bundle-Size bleibt groß

=== Alternative 2: Material-UI (MUI)

* **Pro**: Umfangreiches Component-Set, gute Dokumentation
* **Contra**: Noch größere Bundle-Size, ähnliche CSS-in-JS Probleme

=== Alternative 3: Ant Design

* **Pro**: Viele Enterprise-Features
* **Contra**: Schwieriger zu customizen, große Bundle-Size

=== Alternative 4: Vanilla CSS/CSS Modules

* **Pro**: Maximale Kontrolle, keine Dependencies
* **Contra**: Hoher Entwicklungsaufwand, keine Component-Library

== Konsequenzen

=== Positive Konsequenzen

* **Performance-Verbesserung**:
- Elimination der CSS-in-JS Runtime
- Kleinere Bundle-Size (Reduktion um ~60%)
- Schnellere Initial-Load-Times
- Bessere Performance auf schwächeren Geräten

* **Developer Experience**:
- Schnelleres Hot-Module-Replacement (HMR)
- Direktes Styling im Template
- Bessere IDE-Unterstützung mit Tailwind IntelliSense
- Einfachere Debugging durch Utility-Classes

* **Wartbarkeit**:
- Weniger Dependencies (958 Zeilen Reduktion in pnpm-lock.yaml)
- Konsistentes Design durch Tailwind Config
- Einfachere Updates und Security-Patches

* **Accessibility**:
- Headless UI bietet WCAG-konforme Komponenten
- Keyboard-Navigation out-of-the-box
- Screen-Reader-Support integriert

=== Negative Konsequenzen

* **Migration-Aufwand**:
- Alle Komponenten müssen umgeschrieben werden
- Tests müssen angepasst werden
- Team-Schulung für Tailwind-Ansatz nötig

* **Learning Curve**:
- Utility-First-Ansatz ist gewöhnungsbedürftig
- Tailwind-Klassen müssen gelernt werden

* **HTML-Verbosity**:
- Templates werden durch viele Utility-Classes länger
- Kann initial unübersichtlich wirken

== Implementation

=== Component-Struktur (Atomic Design)

[source]
----
src/components/
├── atoms/           # Basis-Komponenten (Button, Input, Text)
├── molecules/       # Kombinierte Komponenten (PasswordInput, Tabs)
├── organisms/       # Komplexe Module (LoginWindow, UsersTable)
├── templates/       # Seiten-Layouts (DashboardLayout, AuthLayout)
└── pages/          # Route-Komponenten
----

=== Migration-Strategie

1. **Phase 1**: Setup & Core Components (abgeschlossen)
- Tailwind CSS Installation und Konfiguration
- Basis-Atoms (Button, Input, Container, etc.)
- Utility-Functions (cn, utils)

2. **Phase 2**: Complex Components (in Arbeit)
- Molecules (Dialogs, Tabs, Tables)
- Organisms (Forms, Navigation)
- Templates & Layouts

3. **Phase 3**: Cleanup
- Entfernung aller Chakra UI Dependencies
- Test-Anpassungen
- Performance-Optimierung

=== Code-Beispiele

**Vorher (Chakra UI)**:

[source,tsx]
----
import { Button, useColorMode } from '@chakra-ui/react';

export const MyButton = () => {
  const { colorMode } = useColorMode();
  return (
    <Button
      colorScheme="red"
      size="lg"
      variant="solid"
    >
      Click me
    </Button>
  );
};
----

**Nachher (Tailwind + Headless UI)**:

[source,tsx]
----
import { Button } from '@/components/atoms/button.atom';

export const MyButton = () => {
  return (
    <Button
      variant="primary"
      size="lg"
    >
      Click me
    </Button>
  );
};
----
