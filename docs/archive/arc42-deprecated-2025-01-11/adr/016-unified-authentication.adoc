= ADR-016: Unified Authentication
:toc:
:author: Bluelight-Hub Team
:date: 2025-01-24
:status: Akzeptiert und implementiert

== Kontext

Das Bluelight-Hub-System verwendete bisher separate Endpunkte und Formulare für Login und Registrierung. Dies führte zu mehreren Herausforderungen:

* **UX-Probleme**: Benutzer mussten sich merken, ob sie bereits registriert waren
* **Verwirrung**: Neue Benutzer waren oft unsicher, welchen Prozess sie wählen sollten
* **Code-Duplikation**: Separate Formulare und Logik für ähnliche Prozesse
* **Inkonsistente Benutzererfahrung**: Unterschiedliche Flows für im Grunde gleiche Aktionen

In modernen Applikationen wird zunehmend ein vereinheitlichter Authentifizierungsansatz verwendet, bei dem das System automatisch erkennt, ob ein Benutzer existiert und entsprechend handelt.

== Entscheidung

Wir haben uns für die Implementierung eines **Unified Authentication Pattern** entschieden:

=== Architekturelle Änderungen

1. **Ein einziger Auth-Endpunkt**: `/api/auth/unified` ersetzt `/api/auth/login` und `/api/auth/register`
2. **Intelligente Backend-Logik**: Der Service erkennt automatisch, ob ein Benutzer existiert
3. **Einheitliches Frontend-Formular**: Ein Formular für beide Prozesse
4. **Konsistente Response-Struktur**: Gleiche Datenstruktur mit `isNewUser`-Flag zur Unterscheidung

=== Implementierungsdetails

==== Backend (NestJS)

[source,typescript]
----
@Post('unified')
async unifiedAuth(@Body() AuthRequestDto): Promise<AuthResponseDto> {
  const existingUser = await this.findUserByUsername(authDto.username);
  
  if (existingUser) {
    // Login-Prozess
    const isValidPassword = await this.validatePassword(authDto.password, existingUser.password);
    if (!isValidPassword) {
      throw new UnauthorizedException('Invalid credentials');
    }
    return {
      user: existingUser,
      token: this.generateJWT(existingUser),
      isNewUser: false
    };
  } else {
    // Auto-Registrierung
    const newUser = await this.createUser({
      username: authDto.username,
      password: await this.hashPassword(authDto.password),
      email: authDto.email // optional
    });
    return {
      user: newUser,
      token: this.generateJWT(newUser),
      isNewUser: true
    };
  }
}
----

==== Frontend (React)

* Einheitliches Formular mit TanStack Form
* Zod-Validierung für Type-Safety
* Optimistische UI-Updates basierend auf `isNewUser`-Flag
* Toast-Notifications für unterschiedliches Feedback

=== Sicherheitsüberlegungen

1. **Username Enumeration**: 
   - Generische Fehlermeldungen bei falschen Credentials
   - Rate-Limiting auf dem Auth-Endpunkt
   - Optional: CAPTCHA nach mehreren fehlgeschlagenen Versuchen

2. **Passwort-Sicherheit**:
   - Bcrypt für Passwort-Hashing
   - Passwort-Stärke-Validierung (Phase 2)
   - Sichere Token-Übertragung (HttpOnly, Secure, SameSite Cookies)

== Konsequenzen

=== Positive Konsequenzen

* **Verbesserte User Experience**: Benutzer müssen sich nicht mehr entscheiden
* **Reduzierte Komplexität**: Ein Formular, ein Endpunkt, eine Logik
* **Schnellerer Onboarding**: Neue Benutzer können sofort loslegen
* **Wartbarkeit**: Weniger Code zu pflegen und testen
* **Konsistenz**: Einheitlicher Auth-Flow durch die gesamte Anwendung

=== Negative Konsequenzen

* **Security-Risiko**: Potentielle Username-Enumeration (mitigiert durch Rate-Limiting)
* **Weniger Kontrolle**: Automatische Account-Erstellung könnte missbraucht werden
* **Migration**: Bestehende Integrationen müssen angepasst werden

=== Neutrale Konsequenzen

* **Monitoring**: Neue Registrierungen müssen anders getrackt werden
* **Analytics**: Unterscheidung zwischen Login und Registrierung erfordert Backend-Analyse
* **Dokumentation**: API-Dokumentation und Onboarding-Material muss aktualisiert werden

== Alternativen

=== Alternative 1: Beibehaltung separater Flows
* Pro: Explizite Kontrolle, klare Trennung
* Contra: Schlechtere UX, mehr Code

=== Alternative 2: Social Login Only
* Pro: Keine eigene Auth-Verwaltung
* Contra: Abhängigkeit von Drittanbietern, nicht für alle Szenarien geeignet

=== Alternative 3: Magic Links
* Pro: Passwortlos, sicher
* Contra: Erfordert E-Mail-Infrastruktur, langsamer Flow

== Implementierungsstatus

* **Phase 1** (Abgeschlossen): Basic Unified Auth ohne Passwort-Validierung
* **Phase 2** (In Planung): Passwort-basierte Authentifizierung
* **Phase 3** (Zukunft): OAuth2/Social Login Integration
